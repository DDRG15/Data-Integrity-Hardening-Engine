## FINDING 1 — Credential Leak in Proxy Error Detail

**What:** `DIH_PROXY_URL` accepts the format `http://user:pass@host:port`. When a connection through that URL fails, the Python `requests` library embeds the full URL — credentials and all — in the exception message string. `proxy_probe.py` was forwarding that string verbatim into the `error_detail` field of the output CSV and into structured log lines.

**Who:** Any engineer who opens the output CSV or reads the application logs when a proxy connection fails — including anyone the file is shared with downstream.

**When:** Every failed proxy connection attempt: TCP timeout, refused connection, HTTP error from the proxy itself.

**Where:** `src/dih_engine/recon/modules/proxy_probe.py`, function `_via_generic_proxy`, the `except requests.exceptions.RequestException` handler.

**Why:** The `error_detail` field exists to help diagnose failures. The fix was not to remove the diagnostic but to redact the credential segment from the URL before it appears anywhere outside the process.

**How:**
Added `import re` and a pure-function redaction helper at module scope:

```python
def _redact(text: str) -> str:
    return re.sub(r"(https?://)[^:@/]+:[^@/]+@", r"\1***:***@", text)
```

Applied in the exception handler:

```python
safe = _redact(str(exc))
logger.warning("proxy_failed url=%s reason=%s", url, safe)
return {"status": "http_other", ..., "error_detail": f"proxy: {safe[:120]}"}
```

The regex matches `scheme://anything:anything@` and replaces the credential segment with `***:***`. It leaves the host and port intact so the diagnostic remains actionable.

**Test added:** `TestUrlValidation::test_proxy_credentials_not_in_error_detail` — passes a `ConnectionError` with a credential-bearing URL, asserts `"secret"` is absent and `"***"` is present in `error_detail`.

## FINDING 2 — Malformed URLs Misclassified as HTTP Errors

**What:** Entries like `"N/A"`, `"Sin URL"`, or empty strings in the input CSV were passed directly to `requests.Session.get()`. That call raises `requests.exceptions.MissingSchema` or `requests.exceptions.InvalidSchema`, which fell through to the generic `RequestException` handler and produced `status="http_other"`. That status implies an HTTP response was received. No HTTP response was received. The URL was never valid.

**Who:** Any downstream consumer reading the CSV who acts on `http_other` — routing the URL to a fallback module, flagging it for retry, or counting it in error dashboards.

**When:** Every run where the input CSV contains non-URL values in the URL column (common in manually maintained spreadsheets).

**Where:** `src/dih_engine/recon/seer.py`, function `analyze_tech_stack`, before the first `requests_probe.probe()` call.

**Why:** The correct fix is a pre-validation gate. If the URL is structurally invalid, no network call should be attempted and the status must be unambiguous.

**How:**
Added `from urllib.parse import urlparse` and a validation predicate:

```python
def _is_valid_url(url: str) -> bool:
    try:
        p = urlparse(url)
        return p.scheme in ("http", "https") and bool(p.netloc)
    except Exception:
        return False
```

Added an early-return guard at the top of `analyze_tech_stack()`:

```python
if not _is_valid_url(url):
    logger.warning("invalid_url url=%s -- skipping probe", url)
    return ProbeResult(url=url, status="invalid_url", error_detail="malformed URL -- missing scheme or host")
```

**Tests added:** `TestUrlValidation` class — 7 tests covering valid HTTP, valid HTTPS, missing scheme, missing host, non-URL string (`"N/A"`), full `analyze_tech_stack()` integration, and credential redaction.

## FINDING 3 — ThreadPoolExecutor Hangs Indefinitely on Stuck Sockets

**What:** `clean_and_optimize_map()` uses `ThreadPoolExecutor` with `as_completed(futures)` and no timeout. A single URL whose TCP socket enters a half-open state — the connection appears established but the server never sends data — blocks that worker thread for the OS socket timeout, which on Windows defaults to ~4 minutes and is not bounded by the `requests` timeout parameter for the connect phase in all configurations.

**Who:** The operator who runs `dih-engine recon` against a dataset that includes a site behind a crashed FlareSolverr container or a CDN that accepts TCP but drops responses — the CLI appears frozen with no output for minutes.

**When:** Any probe run where at least one URL triggers a fallback chain that ends at a module whose underlying network call is stuck. The `requests` `timeout=` parameter governs read/connect phases but not all scenarios (e.g., FlareSolverr `/v1` container restarting mid-request).

**Where:** `src/dih_engine/recon/seer.py`, `clean_and_optimize_map()`, the `as_completed(futures)` call.

**Why:** The executor must have a wall-clock deadline. Partial results — all URLs that completed before the deadline — are more valuable than no results.

**How:**
Added `import concurrent.futures` and computed a per-run wall-clock budget based on sample size and timeout:

```python
_wall_clock = max(120, (len(sample_urls) * (request_timeout * 4 + 100)) // min(10, len(sample_urls)) + 60)
```

Formula: worst-case per URL is `requests(T) + curl_cffi(T) + flaresolverr(T+60) + proxy(T+30)` ≈ `T*4 + 90`. Divide by parallel workers, add 60s buffer. Floor at 120s.

Wrapped `as_completed()` in try/except and collected partial results on timeout:

```python
try:
    for future in as_completed(futures, timeout=_wall_clock):
        ...
except concurrent.futures.TimeoutError:
    logger.error("probe_pool_timeout wall_clock=%ds -- collecting partial results", _wall_clock)
    for future, url in futures.items():
        if url in done_urls:
            continue
        if future.done():
            all_results.append(future.result())
        else:
            all_results.append(ProbeResult(url=url, status="timeout",
                error_detail=f"probe thread exceeded wall-clock limit of {_wall_clock}s"))
```

**Test added:** `TestCleanAndOptimizeMap::test_missing_input_file_raises` — verifies the executor path is reached and `FileNotFoundError` propagates cleanly before any thread is spawned. The wall-clock path is covered implicitly by the integration tests that mock `analyze_tech_stack` (which must complete without hanging for the test suite to pass in 17s).

## FINDING 4 — Non-Probed URLs Silently Indistinguishable from Probe Failures

**What:** With `sample_size=3` (default), 98 of 101 URLs in a typical CSV are not probed. Before this fix, those rows received `Status=""` (empty string) from `fillna("")`. An empty status is indistinguishable from a probe that returned an empty status string due to a bug, and is easily misread as a successful probe with no status to report.

**Who:** Any data consumer who filters the output CSV for `Status != "ok"` to find actionable failures — they get 98 false positives on every run.

**When:** Every run where `sample_size < total rows`. The default sample is 3; the dataset has 101 URLs.

**Where:** `src/dih_engine/recon/seer.py`, `clean_and_optimize_map()`, the `fillna("")` call on the Status column.

**Why:** A sentinel value makes the not-probed state explicit and filterable. `"not_probed"` cannot be confused with any real probe outcome.

**How:**
Changed one line:

```python
# Before
df["Status"] = df["URL"].map(status_map).fillna("")
# After
df["Status"] = df["URL"].map(status_map).fillna("not_probed")
```

**Test added:** `TestCleanAndOptimizeMap::test_non_probed_urls_get_not_probed_sentinel` — a two-URL CSV with `sample_size=1` confirms the un-probed URL gets `"not_probed"`, not `""`.

## FINDING 5 — Notification Failure Aborts CSV Write

**What:** `notify_all()` was called on the line immediately before `df.to_csv()`. A Slack rate-limit (HTTP 429), a Discord webhook domain resolution failure at 03:00, or any transient network error from either notifier raised an exception that propagated out of `clean_and_optimize_map()` before the CSV was written.

**Who:** The on-call engineer who ran a recon job at 03:00, got a Discord timeout in the logs, and discovered the output file does not exist — meaning the entire probe run must be repeated.

**When:** Any notification failure. Slack and Discord both have documented rate limits; Discord webhooks return 429 after 5 requests/2 seconds.

**Where:** `src/dih_engine/recon/seer.py`, `clean_and_optimize_map()`, the `notify_all()` call.

**Why:** The CSV is the primary output. Notifications are best-effort. Notification failure must never prevent the primary output from being written.

**How:**
Wrapped `notify_all()` in try/except:

```python
try:
    notify_all(tech=winner.tech, strategy=winner.strategy, ...)
except Exception as exc:
    logger.error("notify_all_failed reason=%s -- CSV will still be saved", exc)

df.to_csv(output_file, index=False)
logger.info("master_plan_saved path=%s rows=%d", output_file, len(df))
```

The `df.to_csv()` call is now unconditional. The logger line uses `"CSV will still be saved"` so the on-call engineer reading logs knows exactly what happened and what to check for.

**Test added:** `TestCleanAndOptimizeMap::test_notification_failure_does_not_abort_csv_write` — patches `notify_all` to raise `Exception("channel down")`, asserts the output CSV exists after the call.

## FINDING 6 — GitHub Actions publish.yml Used Unconfigured OIDC

**What:** `.github/workflows/publish.yml` used PyPI's Trusted Publisher (OIDC) mechanism — `id-token: write` permission + `gh-action-pypi-publish` action. That mechanism requires a one-time setup step on the PyPI/TestPyPI web UI (Project → Publishing → Add Publisher) that was never completed. Every push of a version tag would fail at the upload step with a 403 from PyPI before any package was published.

**Who:** Any contributor who tags a release and expects the CI pipeline to publish it — they get a silent failure in the Actions tab with no package on PyPI.

**When:** On every push matching `v*` tags, immediately after the `test` job passes.

**Where:** `.github/workflows/publish.yml`.

**Why:** API tokens are the fallback when OIDC is not configured. They require no PyPI UI setup beyond token creation, and they work immediately.

**How:**
Replaced the OIDC-based `gh-action-pypi-publish` steps with explicit `twine upload` calls using token-based authentication:

```yaml
- run: pip install build twine
- run: python -m build
- run: twine upload --repository testpypi dist/*
  env:
    TWINE_USERNAME: __token__
    TWINE_PASSWORD: ${{ secrets.TEST_PYPI_API_TOKEN }}
```

And for real PyPI:

```yaml
- run: twine upload dist/*
  env:
    TWINE_USERNAME: __token__
    TWINE_PASSWORD: ${{ secrets.PYPI_API_TOKEN }}
```

Required secrets are documented in a comment block at the top of the file. Both secrets must be added in GitHub repo Settings → Secrets → Actions before the pipeline can publish.

**Test added:** No unit test — this finding is a CI configuration issue, not application code. Verification is: tag `v4.0.0`, observe green Actions run, confirm package appears on test.pypi.org.

## Supplementary Changes (Not Audit Findings, Implemented Same Session)

### http_401 and http_521 error code coverage

`requests_probe.py` did not classify HTTP 401 or HTTP 521. Both fell through to `http_other`, which maps to no fallback module in `error_taxonomy.py` — but the correct behavior for each is different:

- **HTTP 401 (Unauthorized):** Terminal. No fallback module can provide credentials. Routing this to `curl_cffi` wastes a network call.
- **HTTP 521 (Web Server Down — Cloudflare):** The origin is unreachable but Cloudflare accepted the connection. `curl_cffi` can sometimes bypass this via a different TLS fingerprint that avoids Cloudflare's intermediate error page.

Added to `requests_probe.py`:

```python
if code == 401:
    return {"status": "http_401", ..., "error_detail": "HTTP 401 Unauthorized -- site requires authentication (terminal)"}
if code == 521:
    return {"status": "http_521", ..., "error_detail": "HTTP 521 Web Server Down -- Cloudflare origin unreachable"}
```

Added to `error_taxonomy.py`:

```python
"http_521": "curl_cffi",  # 521 = Cloudflare can't reach origin; different fingerprint sometimes works
# http_401 intentionally absent -- no fallback can authenticate
```

**Tests added:** `TestBuildProbeResult::test_401_is_terminal_no_fallback`, `TestBuildProbeResult::test_521_maps_to_curl_cffi_fallback`, `TestAnalyzeTechStack::test_401_is_terminal_not_retried`, `TestAnalyzeTechStack::test_521_triggers_curl_cffi_fallback`.
